# Dev Bootstrap v2 아키텍처

v1 기준 리비전 `44c15d5`에서는 setup.sh와 메뉴가 각 설치 함수를 직접 선택했다. v2는 등록된 명령 또는 검증된 계획을 통해 실행한다. 과거 단계와 완료 기준은 [이전 계획](REFACTORING_PLAN.md)에 있다.

## 시작 경로와 호환 경계

`bootstrap.sh`는 인자 배열을 보존해 `setup.sh`로 넘긴다. setup은 공통 lib, 내장 구현 파일과 SSH·gh 전략, core를 고정 순서로 source한 뒤 Registry가 `modules/*/module.sh`를 탐색한다. 고정 파일은 훅이 호출하는 구현 또는 호환 어댑터다. 이 목록은 활성 모듈이나 실행 순서를 결정하지 않는다. 일반 모듈은 자기 디렉터리에서 함수와 설정·명령을 등록한다.

기존 메뉴 2~9와 configure/install은 등록된 같은 명령 함수를 호출한다. 설치 옵션 파서는 공유하고, 버전·방식 전달과 기존 종료 코드 변환은 각 설치 핸들러가 맡는다. 개별 Node·uv 설치의 Shell 복구, 기본 목적지 repo clone의 Workspace 준비, Git 범위 지정과 GitHub doctor의 원격 확인은 기존 명령의 계약이다. 이를 범용 apply로 대체하면 요청 범위나 반환값이 달라진다. 범용 실행은 CLI가 기존 훅의 지역 변수와 복원 목록 스냅샷을 한 번 확정한 뒤 Runner에 계획을 넘긴다. 새 환경명·새 런타임 옵션·셸 조각 선택에는 아직 내장 분기가 남는다.

## 구성과 실행 순서

| 구성 | 소유하는 결정 |
|---|---|
| bootstrap.sh, setup.sh, core/cli.sh, core/menu.sh | 얇은 진입점, 인자 해석, 메뉴 표시와 사용자 선택. list·도움말·메뉴의 모듈 항목은 같은 Registry를 읽는다. 기존 메뉴 번호와 CLI는 어댑터가 담당한다. |
| core/registry.sh | 저장소 내부 modules/*/module.sh 탐색, 계약·중복·참조 검증. 모듈 수가 적어 Bash 3.2 인덱스 배열과 선형 조회로 충분하다. |
| core/planner.sh, core/runner.sh | 프로필에서 순서를 확정하고 실행 전에 전체 계획을 검증한다. Runner는 선행 결과, 플랫폼, check/apply/verify, 결과 요약을 담당한다. |
| modules/<id>/ | 기능별 설정 키·검증·버전 판정·설치·환경 조각을 함께 둔다. SSH와 gh는 github 내부 전략으로 두며 repo clone/remote는 repository 전용 작업으로 둔다. |
| lib/, config/ | 로깅·경로·설정 스냅샷·계정 조회 등의 공통 동작과 환경 선택을 제공한다. lib/shellenv.sh가 조각과 활성 목록을 게시한다. 다운로드 옵션과 검증 기준은 도구별로 달라 실제 공통 동작이 확인된 부분만 추출한다. |

list/help도 설정 로딩과 후보 검증을 거친 뒤 등록 정보를 출력한다. 실행 훅은 호출하지 않는다. 실행은 **탐색 → 설정 확정 → 계획 검증 → 모듈 실행 → 요약** 순서다. classroom은 교육장 전체 구성을, minimal은 Workspace·Git·GitHub·Shell을 선택한다. 기본 계획은 프로필 순서를 보존하고 누락·역순·중복·순환 의존성을 변경 전에 거부한다. 예를 들어 repository 일괄 복원은 workspace와 설정된 인증 방식을 사용한다. 단일 apply는 선택하지 않은 선행 모듈을 읽기 전용으로 확인하고 미충족이면 BLOCKED와 필요한 모듈명을 표시한다. 사용자가 요청한 범위를 넘어 설치하지 않는 대신 선행 모듈을 먼저 실행하는 단계가 필요할 수 있다.

### T16 계획과 T17 실행 경계

`plan`, `all --dry-run`, 기존 `all`과 메뉴 10번은 같은 선행 관계 검사를 사용한다. 계획의 실행 대상은 출력된 모듈 ID와 그 순서다. `shell`을 선택한 일괄 실행에서만 활성 조각 목록을 조정한다. 기존 로더가 있는 HOME에서도 Shell을 생략하면 활성 목록을 보존하고, 명시적인 빈 배열은 코드 0의 빈 계획이다. 이전 환경의 조각을 비활성화하려면 `shell`을 명시한다.

T17에서 CLI는 옵션을 적용한 뒤 Planner가 만든 모듈 인덱스 순서와 유효 선행 목록을 Runner에 전달한다. 선행 Shell이 실패하면 Node·uv Python을 BLOCKED로 처리하고, 후행 훅에서 Shell을 다시 적용하거나 계획 밖의 정리 단계를 추가하지 않는다. 같은 원칙을 Repository의 선행 Workspace에도 적용한다. 단일 대상으로는 Planner가 해당 ID에서 도달하는 선행 관계만 순회해 공유 선행 모듈을 한 번씩 배치한다. Runner는 대상 앞의 모든 모듈을 check 전용으로 실행한다. 일괄 실행은 사용자가 지정한 순서에서 앞서 확정한 결과를 재사용한다. 메뉴 10번과 CLI는 같은 실행 경로를 사용한다.

## 설정 및 셸 마이그레이션

- 기존 Bash 형식은 macOS 기본 도구로 읽을 수 있고 배열과 HOME 확장을 지원한다. source되는 파일은 사용자 자신이 신뢰하는 코드다. 외부에서 받은 설정을 자동 실행하지 않는다.
- 모듈 기본값 → 공통 defaults → 선택된 environments/<이름>.conf → 개인 설정 → 명시적 CLI 순서로 적용한다. 환경 이름은 허용된 식별자로 제한한다. 환경과 계정은 각각 `--environment`와 기존 `--profile`로 고른다.
- 공개 예시는 저장소에, 개인 계정과 복제 목록은 Git에서 제외한다. 기존 profiles.conf는 accounts.conf 전환 기간 동안 지원한다. 둘이 함께 있으면 새 계정 파일의 명시 값이 우선이다. 기존 INSTALL_*는 명시적인 환경 목록이 없는 레거시 구성에서 classroom 선택을 변환할 때만 쓴다. 사용자가 보관한 비밀 없는 계정 설정과 복제 목록을 초기화 후 복구하고 키는 교육장 절차에 따라 다시 생성·등록한다.
- 매 로딩마다 새 기본 상태에서 모듈별 키를 구성한다. 자식 셸에서 선언된 키와 배열 원소를 검증하고 전체 스냅샷이 완성된 뒤 한 번에 교체한다. 삭제된 개인 값은 이전 로딩에서 상속하지 않는다. 메뉴 선택 도중 실패하면 해당 동작을 취소한다.
- 셸 모듈은 .zshrc의 기존 사용자 내용과 단일 관리 로더를 보존한다. 도구는 자기 소유의 env.d 조각을 원자적으로 갱신한다. 관리 목록에 기록된 활성 조각만 순서대로 읽고 PATH는 항목 단위로 중복을 막는다. 전체 프로필 적용 시 비활성 조각은 목록에서 제외하고 파일은 보존한다. 개별 install node/python(uv)은 기존 목록에 자기 조각을 병합한다.
- v1 env.zsh가 알려진 원본과 일치하면 같은 디렉터리에서 임시 파일을 만든 뒤 교체한다. 사용자가 편집한 파일, 심볼릭 링크와 예상 밖 소유권은 보존하고 조치를 안내한다. 기존 설치를 이관할 때 활성 도구의 조각을 먼저 준비한 뒤 로더를 전환한다. 현재 실행에 필요한 경로는 해당 모듈의 자식 셸에서 설정한다. 새 터미널에는 zsh 로더가 적용한다.

초기 이관 함수 `shellenv_migrate <템플릿 디렉터리> [조각 ID ...]`는 단일 로더가 있는 v1 설치를 대상으로 한다. 신뢰하는 호출자가 전달한 순서대로 `env.d/active.list`에 ID를 한 줄씩 기록한다. ID는 영문 소문자로 시작하고 이후 소문자·숫자·밑줄·하이픈을 허용한다. 빈 목록은 아무 조각도 실행하지 않는다. 로더는 목록 전체를 검사한 뒤 해당 `env.d/<ID>.zsh`만 읽는다. 조각은 필요할 때 `dev_bootstrap_path_prepend`로 PATH 한 항목을 관리한다.

조각과 목록을 준비한 후 기존 파일과 같은 내용이거나 비어 있는 이름에만 게시하고, 마지막에 v1과 다시 대조해 같은 파일시스템에서 `env.zsh`를 교체한다. 중단되면 같은 입력으로 재시도한다. 편집 파일이 충돌하면 사용자 검토가 필요하다. 새 설치는 같은 조각을 준비하고 v2 로더를 직접 게시한다.

v2에서는 Shell이 관리하는 목록과 Node·Python 모듈의 템플릿을 별도로 대조한다. 전체 적용은 환경의 모듈 순서와 Python 설치 방식을 따른다. 개별 Node·uv 설치는 기존 목록 순서에 자기 ID만 추가하며, 단일 v1에서 개별 이관할 때는 기존 두 초기화를 보존한다. Source 개별 설치는 셸 설정을 쓰지 않는다. 누락된 관리 조각은 다시 준비하고, 템플릿 갱신은 해당 ID로 게시한 내용의 Git 해시와 일치하는 파일에만 허용한다. `env.d/.managed-*`는 이 비교에 쓰는 빈 파일이다. 조각의 준비·교체가 끝난 뒤 목록을 원자적으로 게시하고, 비활성 파일은 그대로 둔다.
