# Dev Bootstrap v2 아키텍처 제안

검토 기준은 `44c15d5`이다. 현재 실행 방법은 [사용 설명서](USER_GUIDE.md), v1의 운영 제약은 [설계 및 운영 참고](DESIGN_AND_LIMITATIONS.md)에 있다. 아래 v2 명령과 경로는 구현 목표다.

## 현재 한 명령이 실행되는 과정

`bootstrap.sh`는 자신의 위치를 구해 인자를 그대로 `setup.sh`에 넘긴다. 후자는 `pipefail`을 설정하고 다섯 라이브러리와 열 개 모듈 파일을 같은 셸에 정해진 순서로 로드한다. `main`은 도움말 요청에도 설정부터 로드한다. 무인자 실행은 메뉴로 들어가며 선택할 때마다 설정을 다시 읽는다. 메뉴 2번은 Git 작성자 설정이고 0번과 입력 종료는 정상 종료다. CLI와 메뉴가 설치 함수를 별도로 호출하므로 같은 기능에 진입하는 경로가 둘이다.

| 위치 | 현재 책임과 결합 |
|---|---|
| `lib/common.sh`, `logger.sh` | 명령 존재 확인과 메시지 출력. 정보·성공은 stdout, 경고·오류는 stderr로 보낸다. |
| `lib/config.sh`, `config/` | 신뢰한 defaults와 개인 profiles를 자식 셸에서 source하고 고정된 변수 목록을 NUL 구분 스냅샷으로 전달한다. 검증 실패 시 부모 설정을 보존한다. 새 도구의 설정 이름과 검증을 추가하려면 로더를 고쳐야 한다. repositories.conf는 별도의 줄 단위 데이터다. |
| `lib/profiles.sh`, `lib/platform.sh` | 계정·이메일에서 `PROFILE_USER/EMAIL/KEY/ALIAS` 등을 전역으로 채운다. doctor는 macOS, Xcode CLI, Workspace, SSH 설정 및 개별 런타임을 직접 검사한다. |
| `setup.sh` | 옵션 파서가 `PROFILE/METHOD/SCOPE/REPO`와 설치 버전을 공유 변수로 전달한다. `run_install`은 도구별 설치 후처리까지 알고 있다. `run_all`은 순서, `INSTALL_*`, 목록 파싱과 실패 건수를 관리한다. 신규 도구 하나가 help, 메뉴, 분기, 설정, doctor에 모두 영향을 줄 수 있다. |

| 기능 | 의존성과 사용자 환경에 미치는 효과 |
|---|---|
| Workspace, repository | Workspace는 HOME 아래 디렉터리를 만든다. clone은 프로필을 읽고 기본 목적지일 때 Workspace 함수를 호출한다. URL 생성은 파서가 설정한 `REPO_OWNER/REPO_NAME`을 사용한다. Git clone은 파일을 만들고 remote는 지정 저장소의 Git 설정을 바꾼다. 기존 origin이 다르면 실패한다. |
| Git, GitHub | Git은 전역 또는 저장소별 작성자를 쓴다. GitHub는 SSH와 gh에 위임한다. SSH는 키 생성·권한 조정·Include·프로필별 Host 파일을 관리한다. 로컬 설정 성공과 GitHub 공개키 등록은 별개다. gh는 로그인, 사용자 조회, Git credential helper 구성을 수행한다. |
| Node, Python | Node는 curl로 nvm 설치 스크립트를 받아 실행하고 버전과 default alias를 설정한다. Python은 uv 설치와 버전 탐색 또는 소스 다운로드·압축 해제·빌드를 수행한다. 설치 경로는 HOME 아래이며 두 모듈 모두 셸 설정을 호출한다. nvm을 source하면 현재 프로세스 상태도 변한다. |
| Shell, iTerm2 | Shell은 nvm과 Python PATH를 아는 단일 env.zsh를 다시 쓰고 .zshrc에 로더를 추가한다. iTerm2는 Darwin에서 curl과 ditto로 임시 아카이브를 받아 풀고 ~/Applications로 복사한다. 현재 검사 기준은 앱 번들 디렉터리의 존재다. |

현재 `configure`, `install`, `repo clone/remote`, `doctor [github]`, `all`은 보존 대상이다. 단일 명령은 대체로 0 성공, 1 실행 실패, 2 인자·설정 오류, 3 도구·플랫폼 요구, 4 인증·사용자 조치, 5 사후 검증 실패를 사용한다. 일부 하위 명령은 자체 코드를 반환한다. `all`은 문제가 생겨도 다음 단계를 실행한 뒤 0 또는 1로 집계한다. 이 방식에서는 인증이 실패해도 뒤의 복제를 시도하며, 검사 명령이 깨져도 설치가 필요한 것으로 취급될 수 있다.

## 목표 구조와 실행 순서

| 구성 | 소유하는 결정 |
|---|---|
| bootstrap.sh, setup.sh, core/cli.sh, core/menu.sh | 얇은 진입점, 인자 해석, 메뉴 표시와 사용자 선택. list·도움말·메뉴의 모듈 항목은 같은 Registry를 읽는다. 기존 메뉴 번호와 CLI는 어댑터가 담당한다. |
| core/registry.sh | 저장소 내부 modules/*/module.sh 탐색, 계약·중복·참조 검증. 모듈 수가 적어 Bash 3.2 인덱스 배열과 선형 조회로 충분하다. |
| core/planner.sh, core/runner.sh | 프로필에서 순서를 확정하고 실행 전에 전체 계획을 검증한다. Runner는 선행 결과, 플랫폼, check/apply/verify, 결과 요약을 담당한다. |
| modules/<id>/ | 기능별 설정 키·검증·버전 판정·설치·환경 조각을 함께 둔다. SSH와 gh는 github 내부 전략으로 두며 repo clone/remote는 repository 전용 작업으로 둔다. |
| lib/, config/ | 로깅·경로·설정 스냅샷·계정 조회 등의 공통 동작과 환경 선택을 제공한다. 환경 조각을 기록할 때 shellenv를 분리한다. 다운로드 옵션과 검증 기준은 도구별로 달라 실제 공통 동작이 확인된 부분만 추출한다. |

조회는 등록 정보만 읽는다. 실행은 **탐색 → 설정 확정 → 계획 검증 → 모듈 실행 → 요약** 순서다. classroom은 교육장 전체 구성을, minimal은 Workspace·Git·GitHub·Shell을 선택한다. 기본 계획은 프로필 순서를 보존하고 누락·역순·중복·순환 의존성을 변경 전에 거부한다. 예를 들어 repository 일괄 복원은 workspace와 설정된 인증 방식을 사용한다. 단일 apply는 선택하지 않은 선행 모듈을 읽기 전용으로 확인하고 미충족이면 BLOCKED와 필요한 모듈명을 표시한다. 사용자가 요청한 범위를 넘어 설치하지 않는 대신 선행 모듈을 먼저 실행하는 단계가 필요할 수 있다.

### T16 계획과 T17 실행 경계

`plan`, `all --dry-run`, 기존 `all`과 메뉴 10번은 같은 선행 관계 검사를 사용한다. 계획의 실행 대상은 출력된 모듈 ID와 그 순서다. `shell`을 선택한 일괄 실행에서만 활성 조각 목록을 조정한다. 기존 로더가 있는 HOME에서도 Shell을 생략하면 활성 목록을 보존하고, 명시적인 빈 배열은 코드 0의 빈 계획이다. 이전 환경의 조각을 비활성화하려면 `shell`을 명시한다.

T17의 일괄 Runner는 이 계획을 그대로 소비한다. 선행 Shell이 실패하면 Node·uv Python을 BLOCKED로 처리하고, 후행 훅에서 Shell을 다시 적용하거나 계획 밖의 정리 단계를 추가하지 않는다. 같은 원칙을 Repository의 선행 Workspace에도 적용한다. 개별 명령의 복구 어댑터와 향후 단일 `apply`의 읽기 전용 선행 확인은 각각의 계약을 따른다. T16의 기존 일괄 실행기는 계획 검증 후 기존 실패 집계 방식을 사용한다.

## 설정 및 셸 마이그레이션

- 기존 Bash 형식은 macOS 기본 도구로 읽을 수 있고 배열과 HOME 확장을 지원한다. source되는 파일은 사용자 자신이 신뢰하는 코드다. 외부에서 받은 설정을 자동 실행하지 않는다.
- 모듈 기본값 → 공통 defaults → 선택된 environments/<이름>.conf → 개인 설정 → 명시적 CLI 순서로 적용한다. 환경 이름은 허용된 식별자로 제한한다. 환경과 계정은 각각 `--environment`와 기존 `--profile`로 고른다.
- 공개 예시는 저장소에, 개인 계정과 복제 목록은 Git에서 제외한다. 기존 profiles.conf는 accounts.conf 전환 기간 동안 지원한다. 둘이 함께 있으면 새 계정 파일의 명시 값이 우선이다. 기존 INSTALL_*는 명시적인 환경 목록이 없는 레거시 구성에서 classroom 선택을 변환할 때만 쓴다. 사용자가 보관한 비밀 없는 계정 설정과 복제 목록을 초기화 후 복구하고 키는 교육장 절차에 따라 다시 생성·등록한다.
- 매 로딩마다 새 기본 상태에서 모듈별 키를 구성한다. 자식 셸에서 선언된 키와 배열 원소를 검증하고 전체 스냅샷이 완성된 뒤 한 번에 교체한다. 삭제된 개인 값은 이전 로딩에서 상속하지 않는다. 메뉴 선택 도중 실패하면 해당 동작을 취소한다.
- 셸 모듈은 .zshrc의 기존 사용자 내용과 단일 관리 로더를 보존한다. 도구는 자기 소유의 env.d 조각을 원자적으로 갱신한다. 관리 목록에 기록된 활성 조각만 순서대로 읽고 PATH는 항목 단위로 중복을 막는다. 전체 프로필 적용 시 비활성 조각은 목록에서 제외하고 파일은 보존한다. 개별 apply는 해당 항목만 갱신한다.
- v1 env.zsh가 알려진 원본과 일치하면 같은 디렉터리에서 임시 파일을 만든 뒤 교체한다. 사용자가 편집한 파일, 심볼릭 링크와 예상 밖 소유권은 보존하고 조치를 안내한다. 기존 설치를 이관할 때 활성 도구의 조각을 먼저 준비한 뒤 로더를 전환한다. 현재 실행에 필요한 경로는 해당 모듈의 자식 셸에서 설정한다. 새 터미널에는 zsh 로더가 적용한다.

초기 이관 함수 `shellenv_migrate <템플릿 디렉터리> [조각 ID ...]`는 단일 로더가 있는 v1 설치를 대상으로 한다. 신뢰하는 호출자가 전달한 순서대로 `env.d/active.list`에 ID를 한 줄씩 기록한다. ID는 영문 소문자로 시작하고 이후 소문자·숫자·밑줄·하이픈을 허용한다. 빈 목록은 아무 조각도 실행하지 않는다. 로더는 목록 전체를 검사한 뒤 해당 `env.d/<ID>.zsh`만 읽는다. 조각은 필요할 때 `dev_bootstrap_path_prepend`로 PATH 한 항목을 관리한다.

조각과 목록을 준비한 후 기존 파일과 같은 내용이거나 비어 있는 이름에만 게시하고, 마지막에 v1과 다시 대조해 같은 파일시스템에서 `env.zsh`를 교체한다. 중단되면 같은 입력으로 재시도한다. 편집 파일이 충돌하면 사용자 검토가 필요하다. 새 설치는 같은 조각을 준비하고 v2 로더를 직접 게시한다.

v2에서는 Shell이 관리하는 목록과 Node·Python 모듈의 템플릿을 별도로 대조한다. 전체 적용은 환경의 모듈 순서와 Python 설치 방식을 따른다. 개별 Node·uv 설치는 기존 목록 순서에 자기 ID만 추가하며, 단일 v1에서 개별 이관할 때는 기존 두 초기화를 보존한다. Source 개별 설치는 셸 설정을 쓰지 않는다. 누락된 관리 조각은 다시 준비하고, 템플릿 갱신은 해당 ID로 게시한 내용의 Git 해시와 일치하는 파일에만 허용한다. `env.d/.managed-*`는 이 비교에 쓰는 빈 파일이다. 조각의 준비·교체가 끝난 뒤 목록을 원자적으로 게시하고, 비활성 파일은 그대로 둔다.
